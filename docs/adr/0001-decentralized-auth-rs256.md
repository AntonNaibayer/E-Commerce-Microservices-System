# ADR 0001: Как мы проверяем токены без лишних запросов (через RS256)

**Дата:** Август 2026 г.  
**Статус:** Принято

## 1. Контекст
У меня микросервисная архитектура. Когда пользователь хочет положить товар в корзину, он отправляет запрос с JWT-токеном. Возникает проблема: как сервис корзины поймет, что токен настоящий? Если на каждый чих отправлять запрос в сервис авторизации, всё будет тормозить. Нужно, чтобы сервисы проверяли токены сами, но при этом всё было безопасно.

## 2. Рассмотренные варианты
*   **Спрашивать у Nginx или шлюза:** Безопасно, но добавляет лишние запросы по сети, сервисы будут отвечать дольше.
*   **Обычный секретный ключ (HS256):** Создать один секретный пароль и раздать его всем микросервисам. Работает быстро, но небезопасно.
*   **Асимметричное шифрование (RS256):** Использовать пару ключей — приватный и публичный.

## 3. Принятое решение
Я решил использовать **RS256**. Всю логику проверки я вынес в общую папку `libs/shared`, чтобы не писать один и тот же код в каждом микросервисе.

## 4. Обоснование

Алгоритм RS256 решает эту проблему идеально:
1. Только `auth-service` знает **приватный ключ**. Только он может создавать токены.
2. В `libs/shared` лежит только **публичный ключ**. 
3. Когда запрос приходит в корзину, она через публичный ключ проверяет математическую подпись токена. Публичным ключом можно *только проверить* токен, но им нельзя создать новый!

В итоге мы получаем плюсы со всех сторон: токены проверяются моментально (без запросов по сети к auth-сервису), а если кто-то даже утащит публичный ключ из корзины, хакеру он ничем не поможет.

## 5. Последствия
*   Нам не нужно настраивать сложную логику проверки токенов на уровне Nginx, он будет просто проксировать трафик по сервисам.
*   Нужно убедиться, что файл с публичным ключом корректно подтягивается во все контейнеры при сборке Docker.
